OpenAI CFO Sarah Friar is pushing a useful frame: stop asking whether AI is impressive, start asking whether it produces useful work at an acceptable cost.

That sounds obvious. It is not how most teams buy or measure AI right now.

The default evaluation is still demo-first. A model writes a clean email. An agent clicks through a workflow once. A support bot answers a cherry-picked question. Everyone nods, then the tool goes into production and the bill shows up later. Or worse, the hidden bill shows up as rework, escalations, latency, brittle prompts, and employees who quietly stop using the system.

Friar’s proposed scorecard centers on four measures: useful work, cost per successful task, dependability, and return on compute. I like the order. It starts with output, not model capability.

## The unit of value is the completed task

“Useful work” is the right anchor because it forces teams to define the job. Not “we used GPT-5” or “we automated research.” What task was completed? Was it accepted by a human reviewer? Did it move a ticket, invoice, code change, claim, lead, or contract forward?

That framing also exposes a common trap. A model can produce a lot of plausible intermediate work while completing very little. Drafts are not outcomes. Summaries are not decisions. Tool calls are not progress by themselves.

Cost per successful task is the next useful cut. Token spend alone is too crude. So is seat price. If an AI system spends $0.40 to resolve a support issue that used to cost $6, good. If it spends $0.04 to create a bad answer that triggers a refund, bad. The denominator matters.

This is where many pilots break. They measure cost per attempt instead of cost per success. Attempts make AI look cheap. Successes make the economics real.

## Dependability is where ROI gets honest

Friar includes dependability in the scorecard, which is the part most executive dashboards underplay. Reliability is not a technical footnote. It changes the operating model.

A system that is right 95% of the time may be excellent for drafting marketing variants. It may be unusable for compliance review without a human gate. A coding agent that succeeds on small bug fixes may still need tight test coverage before it can touch payments logic. Same model, different risk surface.

Dependability also affects labor savings. If humans must inspect every output at full depth, the tool may be speeding up typing while preserving the real bottleneck. If humans can inspect by exception, with logs, confidence signals, tests, or replayable traces, the economics improve.

This is why return on compute is more interesting than raw compute spend. The question is not whether a company used more GPUs. The question is whether extra inference, retries, retrieval, tool use, or larger models produced enough accepted work to justify the cost.

OpenAI’s framing is practical, but it is still a frame. Friar did not provide public benchmark results or a standard measurement method in the source material. Teams will have to do the dull part themselves: define success, instrument workflows, and resist making the scorecard another vanity dashboard.

## A better scorecard is also a better product brief

The hidden benefit is product discipline. If a team writes these four measures before building, the product gets clearer.

What counts as useful work? What failure rate can the workflow tolerate? What is the current human cost per completed task? Where should the model be cheap and fast, and where should it be slower but more accurate? Which tasks should not be automated at all?

Those questions beat “which model should we use?” almost every time.

Practitioner’s Take: pick one workflow with volume and pain, then measure it for two weeks before adding AI. Count completed tasks, human minutes, error rates, escalations, and current cost per success. Then add the AI system and measure the same things, not just token spend. The catch most readers miss: if you cannot define a successful task before the pilot, you will not be able to prove ROI after it.
