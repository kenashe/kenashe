TL;DR: For hard visual tasks, giving a multimodal model actual tools plus memory that persists across steps beats spending more on raw inference, and OpenVLHarness shows the gap is roughly 9.7 to 12.6 points across 22 benchmarks.

There is a tempting shortcut in agent work: when a model struggles, give it more thinking time. More tokens, higher reasoning effort, bigger budget. It feels like progress because you can watch the model deliberate. The paper I want to walk through, "OpenVLHarness: Real World Visual Agentic Tool-Use with Multimodal Memory" (arXiv, cs.AI/cs.CL/cs.LG), takes that assumption and measures it directly. The result is the kind of finding operators should pin to the wall.

## Does more inference budget actually fix hard visual tasks?

Short answer from the authors: not much. Their controlled study across 22 benchmarks found that simply increasing the inference budget of the base model "yields only modest gains." That is the premise the whole paper is built on, and it matters because the industry default for a stuck model is to throw more compute at it.

The reason is structural, not a tuning problem. A lot of visual tasks need evidence the model cannot generate internally. You cannot reason your way to a precise measurement from a chart. You cannot infer a fact about the real world that is not in the weights. You cannot count objects reliably by staring harder at a thumbnail. These tasks demand grounded perception, external knowledge, and numerical measurements that come from outside the model. No amount of extra deliberation conjures data the model never had.

![a figure straining to think harder next to a figure reaching out to pick up a tool, two paths from the same starting poi](../../assets/blog/2026-10-20-tools-beat-bigger-budgets-for-visual-agents-says-openvlharness/inline-1.webp)

This is the quiet trap in a lot of agent deployments right now. Teams see a weak result, bump the reasoning effort setting, watch the chain of thought get longer, and feel reassured. The paper is a reminder that longer thinking is not the same as new evidence.

## What is OpenVLHarness actually doing differently?

Instead of making the model think more, OpenVLHarness restructures how the model gets and keeps evidence. The authors organize it around two pieces.

First, a capability layer. This combines task-level tool interfaces with what they call evidence rendering. Plain version: the harness gives the model consistent access to a mix of backends (perception tools, web references, measurement tools) and then converts the messy outputs of those tools into observations the model can actually read. That conversion step is the part people underrate. A tool returning raw structured data is useless if the model cannot interpret it. Rendering the output into a model-readable form is half the battle.

Second, persistent multimodal memory. As the model works through a query, the harness retains the images, structured data, and web references it has gathered as addressable artifacts. Not a transcript the model has to re-read, but actual stored objects it can point back to across reasoning steps. There is also a coding interface that executes generated programs over the stored data, so the model can combine results from several tools and run computations on them.

Put together, you get a loop: acquire evidence, inspect it, compose it, repeat. The model is not just a reasoner, it is an investigator with a notebook that does not disappear between steps.

![a loop of gathering, inspecting, and combining pieces that all stay visible in a shared workspace](../../assets/blog/2026-10-20-tools-beat-bigger-budgets-for-visual-agents-says-openvlharness/inline-2.webp)

That memory detail is the one I would flag hardest. Most agent setups lose the thread. Tool output gets summarized into text, the original artifact vanishes, and three steps later the model is reasoning over a lossy paraphrase of something it saw directly. Keeping the artifacts addressable is a different design philosophy, and the numbers suggest it pays.

## How big are the gains, and at what cost?

The headline: OpenVLHarness improves average scores by 9.7 to 12.6 points over matched no-tool baselines across those 22 benchmarks. The authors report the comparison is matched, meaning same backbone, with and without the harness, so the lift is attributable to the scaffolding rather than a stronger base model.

The per-model numbers they give: +11.2 with Qwen3-VL-8B, +9.7 with Kimi K3, and +9.9 with GPT-6 Astra. Worth noting several of those model names (GPT-6 Astra, GPT-6 Luna, Kimi K3) are not products I can independently confirm, and they appear only in this paper, so treat the specific backbone labels as the authors' own naming rather than settled fact. The pattern across eight open and proprietary backbones is the real signal: the harness helps whether the model underneath is small and open or large and closed.

The cost comparison is the part that should make budget-conscious teams pay attention. With GPT-6 Luna at medium reasoning effort, OpenVLHarness reportedly beat the base model, Codex, and Visual Sketchpad running at maximum effort by 7.7 to 8.5 points, while using at most 37 percent of their model-token cost. Read that again. Better results, roughly a third of the tokens. That is the whole thesis in one line: structure beats brute force, and it is cheaper.

I would want to see the per-benchmark spread before celebrating, because an average lift can hide tasks where the harness does nothing or hurts. The abstract gives aggregates, not the distribution. That is the honest caveat. But the direction is consistent enough across eight backbones that I do not think it is a fluke of one favorable benchmark.

## What an operator should take from this

The transferable idea does not depend on any specific model. If your multimodal agent is stuck, the first instinct should not be "raise the reasoning effort." It should be "what evidence does this task need that the model cannot produce on its own, and do I have a tool and a memory layer that can supply it."

![a contrast between a single large glowing brain and a smaller brain surrounded by well-organized instruments](../../assets/blog/2026-10-20-tools-beat-bigger-budgets-for-visual-agents-says-openvlharness/inline-3.webp)

Three concrete things to try. One, audit where your agent loses evidence. If tool outputs get flattened into text and the originals are discarded, you are leaking information every step. Store artifacts you can reference, not summaries. Two, make tool output model-readable on purpose. A raw API response is not an observation; the rendering step the paper describes is real engineering, not a nice-to-have. Three, add a code execution path over your stored data so the model can compute across tools instead of eyeballing numbers it is bad at.

The catch most readers will miss: this is more engineering, not less. A harness with a capability layer, artifact memory, and a code sandbox is harder to build and operate than turning a dial from medium to high. The paper is not selling a free lunch. It is selling a better place to spend your effort. For teams that have been maxing out inference budget and watching costs climb while accuracy plateaus, that trade is worth making. Build the scaffolding once, and you get better answers at a third of the token cost on every query after. Spend tokens on thinking, and you pay that tax forever.
