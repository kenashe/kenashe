A controlled minimal-pair study circulating on Hacker News asks a useful question: does code cleanliness affect coding agents?

That sounds obvious until you try to measure it. Humans care about clean code because we have to read it, hold pieces in memory, infer intent, and avoid breaking hidden assumptions. Coding agents do the same, just with different failure modes. They do not get tired in the human sense. They do lose track. They overweight nearby context. They pattern-match names. They sometimes preserve bad structure because it looks intentional.

So the interesting part is not “clean code good.” The interesting part is whether cleanliness becomes a measurable input to agent performance.

## The repo is part of the prompt

Most teams still treat prompts as the text they type into Cursor, Claude Code, Codex-style tools, or a chat window. That is too narrow. For a coding agent, the prompt is also the repository.

Function names are instructions. File boundaries are hints. Tests are examples. Type signatures are contracts. Comments are weak signals, sometimes useful, sometimes stale. A messy service with vague names and long files does not just slow down humans. It gives the agent fewer stable handles.

A minimal-pair design is the right instinct here because it tries to hold functionality constant while changing presentation. Same behavior, different cleanliness. If the agent does better on the cleaner version, that points to something more specific than “better projects are easier.” It suggests agents are sensitive to software legibility itself.

I would not overread one study from a Hacker News link. We do not have enough here to judge the task set, model mix, scoring method, or whether the differences survive across languages and repo sizes. But the question lands because it matches what many builders already see in practice. Agents do better when the target is local, named clearly, covered by tests, and surrounded by examples that look like the desired change.

## Cleanliness is not aesthetics

The word “clean” can be slippery. Agents probably do not care whether a senior engineer finds the code elegant. They care about signals that reduce ambiguity.

Small functions help because the agent can reason about a unit without dragging in half the repo. Descriptive names help because the model has seen millions of similar names tied to similar intent. Consistent patterns help because the agent can copy the local house style instead of inventing one. Tests help most of all because they turn intent into executable feedback.

The failure case is also familiar. Ask an agent to add a feature in a messy codebase and it may create a parallel abstraction instead of extending the existing one. It may miss the one weird validation path hidden in a 900-line file. It may edit the wrong layer because the boundaries are implied, not expressed. Then the team blames the model.

Sometimes the model is the problem. Sometimes the repo is asking a vague question.

This matters for evaluation too. Benchmarks often measure agents against issue tasks, unit tests, or synthetic coding problems. That is useful, but it can hide a big variable: codebase legibility. The same agent may look weak in a tangled repo and strong in a tidy one. If a study can isolate that variable, even roughly, it gives teams a better way to think about adoption. Not “will agents replace engineers?” More like “what shape of code lets agents contribute without creating cleanup debt?”

## Refactoring may pay twice now

There is an old argument for refactoring: it helps future humans move faster. The agent era adds a second payoff. Refactoring may also improve machine assist.

That changes prioritization. A cleanup task that seemed nice-to-have last year may now increase the success rate of every future agent edit in that area. Better names, narrower modules, stronger tests, and explicit interfaces are not just engineering hygiene. They are scaffolding for automated work.

The catch is that teams should not refactor for the agent alone. You can make code overly fragmented, over-commented, or too pattern-heavy. Agents are good at mimicking local style, including bad local style. If you create ceremony, they will produce more ceremony.

A builder should try this in one repo section, not across the whole codebase. Pick a module where agents often fail. Rename the worst abstractions, split the longest functions, add characterization tests, and write one or two clear examples of the preferred pattern. Then rerun the same agent task before and after. The catch most readers miss: model choice matters, but the cheapest performance gain may be changing the code the model has to read.
