A Hacker News poster put a clean name on a feeling many developers have with Claude Code, Codex, and similar tools: the model may help, but the interaction kills flow.

The line that stuck with me was not about accuracy. It was about rhythm. AI coding feels like “a bicycle that just brakes abruptly every couple minutes.” Stop. Wait. Review. Prompt again.

That is the core product problem.

## The prompt loop is a bad default for coding

Prompt-response is natural for chat. It is not natural for programming.

Programming already has a tight feedback loop: read code, hold context in your head, make a change, run something, inspect the result, adjust. The best tools compress that loop. A good editor, a fast test runner, a language server, a debugger, even plain old autocomplete, they all keep your hands and attention close to the work.

The current coding-agent loop often does the opposite. It asks the developer to step out of the code and into management mode. You write a task description. The model thinks. It edits. You wait. Then you audit a diff you did not write.

That can be great for chores. Rename this, migrate that, scaffold the obvious thing, add tests around a known path. But for design work, debugging, and code with many hidden constraints, the interaction tax gets expensive fast. The human loses the local mental model, then has to rebuild it by reading generated changes.

This is why the Hacker News post’s “tab model” comment matters. Tab completion is not just a smaller UI. It is a different contract. The assistant proposes near the point of intent, and the developer accepts, rejects, or edits without leaving the current frame. The machine becomes a continuation of the hand, not a junior engineer waiting for tickets.

## Better coding AI may look less like chat

I do not think the answer is simply “make agents faster.” Latency matters, but flow breaks for more reasons than waiting.

Review burden is the bigger one. If a model changes ten files, the user now owns every line. That is fine when the task is isolated. It is painful when the change touches architecture, tests, types, naming, and production assumptions. The UI says “done.” The developer’s brain says “now the real work starts.”

The next useful wave of coding tools may be less theatrical. Less “agent goes away and builds feature.” More inline planning, constrained edits, reversible suggestions, and continuous small proposals. Think of tools that can shadow the developer’s current intent and offer the next slice: a function body, a test case, a refactor patch, a likely bug fix, a missing import, a migration step.

There is still room for agent mode. Sometimes you do want to hand off a bounded job. But the product should make the boundary explicit. Is this a co-pilot action inside my flow, or am I delegating a task that I will later review? Mixing those modes is where frustration grows.

The subtle trap is that demos reward delegation. Real coding rewards rhythm.

## The missing unit is attention

Most benchmarks measure whether the model produced the right code. Builders should also measure how often the tool interrupts the programmer’s attention.

How many times did the user switch from editing to supervising? How much generated code had to be read before the next meaningful keystroke? Did the tool preserve the developer’s current mental stack, or did it replace one task with another task called “review the AI”?

Those are product metrics, not model metrics. And they explain why a weaker inline suggestion can feel better than a stronger agent response. The weaker tool stays in the groove.

If I were building with these tools this week, I would split work into two lanes. Use Claude Code or Codex for bounded chores with clear acceptance checks: add fixtures, port a small module, write tests for a stable API, explain an unfamiliar file. For active feature work, keep AI close to the cursor. Ask for the next patch, not the whole feature. Accept small diffs only when you can understand them immediately. The catch most readers miss: the goal is not to maximize generated code. It is to protect your working memory while letting the model remove friction.
