## The agent stack is a bottleneck, not a brain trust

The common story for multi-agent systems is that many specialized agents can “collaborate” better than one big agent. Planner, researcher, critic, coder, judge. Sounds like a software org chart. Sometimes it works. Sometimes it adds latency, cost, and failure modes.

A new arXiv paper, cross-listed in cs.AI and cs.LG, gives a cleaner frame: multi-agent systems help when they compress context well.

The authors’ key observation is simple. A single-agent system keeps one accumulated reasoning trace in one shared context. A multi-agent system splits work into isolated local contexts, then passes bounded relay messages between them. That relay is the whole game.

If the relay has infinite bandwidth, the paper argues, a multi-agent system can simulate a single-agent system by transmitting the full upstream context. No magic there. The interesting case is bounded communication, where each agent has to summarize, filter, or translate what came before.

That creates the real trade-off. Compression can remove junk. It can also lose the one detail the next step needed.

## Weak models may like structure more than strong models do

The paper formalizes this as an information bottleneck, controlled by an effective parameter $β$, which represents the balance between useful context reduction and harmful information loss. You do not need the math to get the practical point: multi-agent design is not automatically better. It is a bet that the messages between agents are near-sufficient.

The authors ran 18 controlled experiments across five benchmarks and three model scales. Their reported pattern is useful because it matches what many builders see in the wild. Multi-agent systems helped when the relay messages preserved enough task-relevant information, especially for weaker models. When the relay dropped important information, gains shrank or reversed, especially for stronger models.

That last clause matters.

A stronger model can often extract signal from a messy, redundant context. It may not need a group of smaller contexts connected by summaries. In fact, the summaries can become lossy middle management. You pay for extra calls, wait longer, and make the system less observable, while the best model in the chain is deprived of raw material it could have used.

This is one reason “agentic” demos can look better than deployed systems. The demo task has clean boundaries. The handoffs are obvious. The relay message is enough. Real work is uglier. Requirements leak across stages. User intent changes. Small details buried in the first prompt become decisive three steps later.

## Design the handoff before adding the agent

The paper’s frame pushes against a lot of current product design. The question should not be, “Can we add a critic agent?” It should be, “What exact information must cross this boundary, and what can be safely thrown away?”

If the answer is fuzzy, a second agent may just add a place to lose state.

The strongest use case is still real: decomposition with disciplined interfaces. A retrieval agent that returns cited evidence. A code-review agent that only checks diffs against tests. A planner that emits a constrained task graph. These are not vibes-based coworkers. They are compression stages with contracts.

The weaker use case is the agent group chat. Several LLMs pass prose back and forth, each assuming the last one preserved the important bits. That can work on simple tasks. It can also create confident drift, where every handoff sounds reasonable and the final answer is missing the thing that mattered.

For a builder, I would test multi-agent designs by measuring the relay, not the persona. Run the same task as one long-context agent, then as split agents with fixed message budgets. Inspect what gets lost at each boundary. Try smaller relays until quality breaks, then decide whether the cost and latency savings are worth it. The catch most readers miss: the agent is rarely the product. The handoff is.
