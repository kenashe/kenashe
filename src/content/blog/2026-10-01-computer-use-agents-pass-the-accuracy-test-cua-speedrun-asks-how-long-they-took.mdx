TL;DR: Computer-use agents already beat humans on accuracy benchmarks, but nobody could reliably measure how slow or expensive they are, and cua-speedrun fixes that with standardized infrastructure that reveals speed, cost, and accuracy almost never line up behind one model.

The headlines on computer-use agents have been about accuracy. An agent drives a browser, clicks through a form, books a flight, and scores well on a long-horizon task suite. Impressive. Also mostly beside the point if you actually want to deploy one. The question an operator asks is not "can it do the task" but "how long does it take, and what does each run cost me." Until now that second question had no clean answer, because the benchmarks measuring it were running on wildly different hardware and container setups.

That is the gap cua-speedrun goes after. The paper, titled "cua-speedrun: Standardized Benchmarking of the Speed of Computer-Use Agents," landed across arXiv's cs.AI, cs.CL, and cs.LG listings, with all code and infrastructure posted at cuaspeedrun.com. The premise is simple and slightly embarrassing for the field: we have been timing races where every runner used a different track.

## Why can't we just compare computer-use agents on speed already?

Because the benchmarks confound the thing they claim to measure. A computer-use agent, or CUA, works by taking screenshots of a graphical interface, reasoning about what it sees, and issuing clicks and keystrokes. Every step in that loop touches a virtual machine: the agent sends an action, the environment renders a result, the agent reads the new screen. The speed of that loop depends heavily on the machine spec, the container configuration, and the network latency between agent and environment.

So when one lab reports its agent finishes a task in 40 seconds and another reports 90, you genuinely cannot tell whether one model is faster or one just ran on a beefier box with lower input-output latency. The authors call this a reproducibility crisis, and that is not hyperbole for a field trying to make deployment decisions. Accuracy is portable across setups. Wall-clock time is not.

cua-speedrun's answer is to hold the environment constant. One uniform virtual machine setup, one execution pipeline, and a common agent interface so a single agent implementation can run across four different CUA benchmarks without rewriting glue code for each. Freeze the track, then time the runners. It sounds obvious in hindsight, which is usually the sign of useful infrastructure.

## What did standardizing the setup actually reveal?

Three findings stand out, and two of them are counterintuitive enough to matter.

First, no single model family wins on all three of speed, cost, and accuracy. This is the one most people guess wrong. We tend to assume the strongest model is also the one you deploy, that capability subsumes efficiency. The paper says no. The fast model is often not the cheap one, and the accurate one is often neither. You are picking a point on a triangle, not climbing a single ladder.

Second, and this is the part that breaks intuition: for some models, increasing the reasoning effort can speed up task completion. More thinking, less total time. The mechanism is not spelled out in the abstract, but the logic writes itself if you have watched agents flail. An agent that reasons harder up front takes fewer wrong turns, and fewer wrong turns means fewer expensive screenshot-reason-act loops. A shallow agent is fast per step and slow overall because it wanders. Depth buys you a straighter path.

Third, faster environment input-output can sometimes slow down overall task completion. That one is genuinely strange on first read. If the environment responds quicker, the whole thing should finish sooner, right? Not necessarily. My read: when the environment feeds results back faster, some agents act more impulsively, firing off actions before a page has settled or before reasoning has caught up, and then burn steps recovering. Speed in the loop is not the same as speed to the goal. The authors flag this as unintuitive, and they are right to.

![a triangle with three pulling corners and a point that cannot sit at all three at once](../../assets/blog/2026-10-01-computer-use-agents-pass-the-accuracy-test-cua-speedrun-asks-how-long-they-took/inline-2.webp)

There is also a sobering line for the open-source crowd: none of the open-weight models are on the frontier here. On accuracy benchmarks open models have been closing the gap. On the speed-cost-accuracy frontier for computer use, they are not yet in the lead group. Worth watching whether that holds as Qwen, Llama-derived, and other open agents get purpose-tuned for GUI control.

## Does this make benchmarking cheaper to run too?

Yes, and this is the quietly practical part. The team shows you can shrink the evaluation task set of most CUA benchmarks without losing statistical power. In plain terms, a lot of benchmark tasks are redundant. They measure the same thing twice. Trim the set carefully and you get the same ranking confidence for a fraction of the compute and time.

For anyone who has waited hours and paid real money to run a full agent benchmark, that is not a footnote. It means faster iteration cycles when you are tuning a harness or comparing two models, and it means the cost of doing honest evaluation drops. Cheaper evals get run more often. Evals that get run more often catch regressions you would otherwise ship.

I want to flag the usual caveat: a standardized VM is a controlled lab, not your production stack. The whole value of holding the environment constant is that it isolates the agent, which also means the absolute numbers will not match what you see on your own infrastructure with your own latency. Use cua-speedrun for relative comparison between agents and configs, not as a promise of production wall-clock time. The paper's own findings about environment latency are the warning label here.

## The Practitioner's Take

If you are picking a computer-use agent for a real workflow, stop treating the accuracy leaderboard as the whole decision. Define your actual constraint first. If you are running thousands of tasks a day, cost per task dominates and you want the cheap-but-adequate corner of the triangle. If a human is waiting on each result, latency dominates and you pay up for speed. If the task is high-stakes and infrequent, accuracy wins and you eat the cost and the wait. cua-speedrun's standardized harness is the tool for measuring those tradeoffs without fooling yourself, so clone the setup at cuaspeedrun.com and run your candidate models through it before you commit.

Two concrete experiments to try: sweep the reasoning-effort setting on your chosen model and watch total completion time, not just per-step time, because the paper suggests the fast-cheap assumption may be backwards for your model. And use the reduced task set to run that sweep at a fraction of the cost. The catch most readers will miss is the environment-latency finding. If you benchmark on a snappy local VM and deploy against a slow remote one, your agent's behavior can change, not just its speed, and the model that won your test may not be the one that wins in production. Measure on infrastructure that resembles where it will actually run.
