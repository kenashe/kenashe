TL;DR: The useful read on Richpanel’s 50% support automation claim is not “AI replaces support,” it is “AI works when it is tied to tools, procedures, and clear handoff rules.”

## What did OpenAI actually claim?

OpenAI’s primary source here is its blog post, “Richpanel helps companies automate 50% of support in 30 days.” The claim is clean and punchy: Richpanel helps companies automate half of support within 30 days.

That is a first-party case study, not an independent benchmark. So I would treat the number as a useful signal, not a universal conversion rate. Support queues vary wildly. A Shopify merchant with repetitive order-status tickets is not the same as a B2B platform handling billing disputes, access control, and angry enterprise admins.

The more interesting detail is how Richpanel is using different models for different jobs. OpenAI says Richpanel uses GPT-6 Astra and GPT-6.1 Sol to equip its AI support agents with tools and procedures, while GPT-6 Luna handles the conversations.

That split matters. It says the product is not just throwing a general chatbot into a helpdesk. It is separating the system into at least two layers: one layer for deciding what can be done, which tools to use, and which procedure applies, and another layer for talking to the customer in human language.

That is how useful agents are starting to look in production. Less sci-fi autonomy. More controlled execution.

## Why does the model split matter?

Customer support is a trap for generic AI demos. The easy demo is a bot that sounds empathetic. The hard product is a bot that knows when to refund, when to escalate, when to check order status, when to follow policy, and when to shut up.

A conversational model alone is not enough. It can say the right-sounding thing while doing the wrong operational thing. That is worse than a bad chatbot because it creates confidence where the company needs control.

Richpanel’s described setup points in the right direction. Procedures and tools are not side features. They are the product. The model needs access to the helpdesk context, customer records, commerce data, internal policy, and escalation path. It also needs constraints. “Be helpful” is not a support policy.

The 50% figure, if it holds for the right customer segment, probably comes from repeatable ticket classes. Order status. Return windows. Basic troubleshooting. Subscription changes. FAQ flows that require one or two system actions.

The remaining 50% is where the business risk lives: edge cases, angry customers, policy exceptions, fraud, compliance, high-value accounts, and anything involving judgment. The trick is not to automate everything. The trick is to know which tickets should never touch full automation.

## What should support teams copy?

Do not copy the headline. Copy the shape of the system.

Start by classifying tickets by action, not topic. “Refund request” is less useful than “refund request under policy,” “refund request outside policy,” and “refund request with fraud signal.” Each class needs a decision rule, a tool path, and a fallback.

Then test against your actual queue. Pull 200 recent tickets. Mark which ones could have been resolved if the agent had the right tools and policy access. Mark which ones needed a human. That gives you a grounded automation target before anyone buys software or celebrates a benchmark.

Also measure containment carefully. A ticket is not automated because a bot replied. It is automated when the customer’s issue is actually resolved, without creating a later contact, a refund error, or an escalation mess. First-contact resolution, reopen rate, CSAT, escalation accuracy, and policy violation rate matter more than deflection as a vanity metric.

Practitioner’s take: if I were implementing this, I would pick one narrow support lane, give the agent only the tools needed for that lane, write explicit “must escalate” rules, and run it in shadow mode before customers see it. The catch most teams miss is that the model is rarely the bottleneck. The bottleneck is messy procedure design, missing tool access, and support policies that humans understand only because they have been improvising around them for years.
