TL;DR: Higher benchmark scores are not the same as more shipped code, so teams should test coding models against their own merge flow before treating leaderboard gains as productivity gains.

## What did the paper actually test?

The primary source is the arXiv paper “Higher-Scoring Coding Models Did Not Get More Work Done,” listed under cs.AI and cs.LG. Its claim is narrow, useful, and uncomfortable for anyone buying coding tools off benchmark deltas.

The paper uses a natural experiment. On June 12, 2026, a U.S. export control directive banned access to Claude Fable 5 for 19 days. Most former Fable 5 users switched to Opus 4.8 during that window. According to the paper, Opus 4.8 scored 11 points lower than Fable 5 on SWE-Bench Pro.

That created a cleaner comparison than the usual “we tried a new model and it felt better” story. The people and projects mostly stayed the same. The model changed.

The researchers tracked GitHub pull requests from 297 Fable 5 users before, during, and after the suspension. They used 8,908 developers who stayed on Opus 4.8 as the control group. They also repeated the comparison across five model upgrades in 2026, covering 1,208 developers and 15,442 pull requests.

The result: access to Fable 5 increased the 7-day merge rate by 1.4 percentage points, with a confidence interval from -1.4 to +4.3. Not statistically significant. Across the five model upgrades, the weighted mean effect was -0.9 percentage points, with intervals that included zero. The paper also did not find a significant increase in merged pull requests per week, reporting +2.4% with a range from -4.9% to +10.2%.

That does not mean better coding models are fake. It means this benchmark gap did not show up as a measurable shipping advantage in this setting.

## Why might a better benchmark score fail to move merge rates?

Because software teams do not ship benchmark tasks. They ship through review, tests, CI, product constraints, legacy code, flaky dependencies, security rules, and human taste.

A model can win on SWE-Bench Pro by being better at isolated repository issues. That is valuable. But a pull request merge rate is downstream of many other bottlenecks. If review queues are slow, if specs are vague, if a codebase has weird internal conventions, or if a team rejects large AI-generated diffs, the model’s extra benchmark skill may never become merged work.

There is another possibility: developers already route around model weaknesses. If Opus 4.8 was “good enough” for common coding tasks, then Fable 5’s advantage may only matter on the hardest slices. Averages can hide that. The paper’s aggregate finding does not prove nobody benefited. It says the measured population did not, on average, ship more merged PRs in a statistically clear way.

The metric matters too. Merge rate is not the whole job. A better model could reduce time spent drafting code, improve tests, help with debugging, or make developers less miserable, without changing the 7-day merge rate. It could also create more plausible bad code, which slows review. The paper does not settle all of that.

But it does put pressure on a lazy assumption: higher coding benchmark score equals higher team productivity. That chain has missing links.

## How should teams evaluate coding models now?

Use benchmarks as a first pass, not as the purchase order.

A coding model evaluation should include the boring internal stuff: time to first acceptable patch, review cycles, CI pass rate, defect rate after merge, size of diffs, rollback frequency, and whether senior engineers trust the output enough to keep using it. If you have agents writing code, measure task completion inside your repo, with your tests, your style rules, and your review policy.

The paper’s design is useful because it looks at real developer behavior instead of synthetic demos. It is also limited because the shock lasted 19 days, the main treated group had 297 users, and pull request outcomes are noisy. I would not overread it into “benchmarks are useless.” I would read it as “benchmarks are incomplete, especially for agents that operate inside messy human systems.”

This is where evals need to get more operational. Not just “can the model solve the issue?” but “does this model help our team get safe, reviewed, maintainable changes into production faster?” Those are different questions.

If you run a dev team, try a two-week model bakeoff on real backlog items with matched task types. Keep the workflow constant. Track merged PRs, review comments, CI failures, and developer time, not just subjective preference. The catch most readers miss: the model may not be your bottleneck. Your review process, test suite, task breakdown, or repo hygiene may erase the gains from a smarter coding agent.
